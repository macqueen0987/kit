# agent-gate 파일럿 리포트

- 일자: 2026-08-28
- 범위: `agent-gate` 토큰 스왑 전체(Task 5) + 설정 패널(`panel-settings`) 유틸리티 전환(Task 6)

## 1. safelist 구멍

파일럿에서 실제로 필요했던 클래스가 번들에 없어서 조용히 안 먹은 사례들이다. 개별 클래스가 아니라 스케일 단위로 safelist에 반영했다 — 근거는 계획 Step 2: "`w-32` 하나가 필요했다면 `w-{16,24,32,48}`을 넣는다. 같은 이유로 다시 돌아오지 않게 한다."

| 필요했던 클래스 | 용도 | 실제 상태(전환 당시) | 조치 |
|---|---|---|---|
| `gap-2.5` (10px) | `check-row`의 원래 `gap: 10px` 재현 | 없음. kit gap 스케일이 `gap-2`(8px)→`gap-3`(12px)로 건너뜀 | `p/px/py/.../gap/gap-x/gap-y` 공용 스케일에 `2.5`, `3.5`를 추가해 하프스텝 전체를 채웠다. `gap-2.5` 하나만 넣으면 다음에 `p-2.5`가 똑같은 이유로 또 빠진다 |
| `min-w-*`, `min-h-*` 숫자 스케일 | `field-row .field { min-width: 140px }`, 체크박스 라벨의 44px 터치 타깃(`min-h-11`) | **숫자 스케일 자체가 전무.** `min-w-0`/`min-w-full`, `min-h-0`/`min-h-full`/`min-h-screen`만 있었다. Task 6 보고서는 이를 "`min-h-11`이 `h-10`과 `h-12` 사이에서 빠졌다"고 적었는데, 이는 부정확한 진단이다 — `h-*`에는 애초에 숫자 스케일이 있고 `min-h-*`에는 없었으므로, 갭은 값 하나가 아니라 스케일 전체였다 | `w`/`h`가 이미 갖고 있던 숫자 스케일(`4,5,6,8,10,12,16,20,24,32,48,64`)에 `11`을 더해 `min-w`/`min-h`에도 동일하게 적용했다(`{w,h,min-w,min-h}-{...,11,...}`). `size-*`에도 `11`을 추가했다 |
| 4px급 `rounded-*` | `.check-row code`의 원래 `border-radius: 4px`, 인라인 코드 칩 | `rounded-sm`이 이론상 후보였으나, agent-gate `:root`가 `--radius-sm`을 8px로 재정의해 kit의 `--radius-sm`(기본값 0.25rem=4px)을 덮어쓴다. 결과적으로 `rounded-sm`을 써도 8px가 나온다 | **safelist만으로는 고칠 수 없는 문제다** — 값 자체가 아니라 변수 이름 충돌이기 때문이다. `tokens.css`에 `--radius-xs: 0.25rem`(4px)을 kit이 직접 통제하는 값으로 새로 정의하고, `rounded-xs`를 safelist에 추가했다. 서비스가 `--radius-xs`를 재정의하지 않는 한 항상 4px가 나온다. `rounded-sm` 자체의 충돌은 고치지 않았다 — kit 쪽 문제가 아니라 서비스가 kit과 같은 변수 이름을 재사용한 결과이므로, 표준 마이그레이션 절차(§ 아래)에 "서비스 고유 변수명이 kit 토큰 이름과 겹치지 않는지 확인" 항목으로 남긴다 |
| 체크박스/토글 컴포넌트 | `.check-row input`의 `accent-color`, 크기 | **kit에 checkbox/toggle 컴포넌트가 전혀 없다.** 유틸리티도, 컴포넌트 클래스도 없다 | 이번 태스크에서는 만들지 않는다. `.check-row input`에 최소 커스텀 CSS(`accent-color: var(--accent)` 등)를 남기는 것 외에 방법이 없었다. **다음 서비스로 넘어갈 최우선 후속 작업**으로 기록한다 — 설정 화면이 있는 서비스라면 반드시 다시 마주친다 |

빌드하고 `pnpm test`로 확인한 결과, 위 클래스들이 실제로 `bundle/dist/app.css`에 생성된다(`tests/bundle.test.mjs`에 대표 클래스 검증 추가, 26/26 통과).

## 2. 토큰 공백

`--info`(정보), `--planned`(계획 상태) 두 개는 kit 토큰에 대응이 없어 agent-gate `:root`에 서비스 고유값으로 남겼다.

```css
--info:        oklch(0.740 0.130 240);
--planned:     oklch(0.800 0.090 300);
```

둘 다 kit accent 규율(L 0.70~0.83, chroma 0.09~0.13)과 정합하고, on-accent 대비도 각각 8.73:1 / 10.32:1로 AAA를 통과한다. 다른 서비스에서도 "정보"·"계획" 같은 상태 색이 반복해서 필요해지면 kit으로 승격을 검토한다. 지금은 파일럿 하나만으로는 판단을 보류한다 — 반복 여부를 확인할 두 번째 사례가 필요하다.

## 4. 예상과 달랐던 것

### 4.1 CSS Cascade Layers가 조용한 실패의 두 번째, 더 위험한 경로다

스펙 §11.1은 조용한 실패의 원인을 "safelist에 없는 클래스를 쓰는 것" 하나로만 짚었다. 파일럿은 그보다 더 위험한 두 번째 경로를 드러냈다.

**증상**: Task 6에서 설정 패널을 `.card-body flex flex-col gap-5` 등 kit 클래스로 전환했는데, 브라우저에서 카드 안쪽 여백이 전부 사라졌다. 클래스는 마크업에 정확히 붙어 있었고, 삭제된 CSS 규칙도 없었다. `getComputedStyle`로 확인한 `.card-body`의 padding은 `0px`였다.

**원인**: kit 번들은 Tailwind v4라 모든 규칙이 `@layer properties, theme, base, components, utilities` 안에 있다. 반면 `dashboard.css`의 전역 리셋 `*, *::before, *::after { margin:0; padding:0; }`은 **레이어 없이(unlayered)** 선언돼 있었다. CSS Cascading and Layers 명세상, 레이어 없는 일반 선언은 **명시도(specificity)나 소스 순서와 무관하게** 어떤 레이어 안의 선언보다 항상 이긴다. `.card-body`의 명시도가 `*`보다 높아도 소용없다 — 레이어 비교가 명시도 비교보다 먼저 일어나기 때문이다.

**정확한 표현이 중요하다.** 이 계획의 앞선 기록(Task 6 보고서 요약)은 `.input`/`.btn` 같은 컴포넌트 클래스가 kit을 이기는 이유를 "명시도 동률에서 dashboard.css가 이긴다"고 서술했는데, 이는 틀렸다. `.input`/`.btn`은 애초에 레이어 없이 선언돼 있어서 **명시도와 무관하게 항상** kit(레이어 안)을 이긴다 — "동률에서 이긴다"가 아니라 "레이어 비교 단계에서 이미 결판난다". 이번 리포트에서 정정한다.

**수정**: 문제가 된 리셋 규칙을 kit과 같은 이름의 `@layer base`로 감쌌다. kit의 Preflight도 `@layer base`를 쓰고, kit의 `<link>`가 `dashboard.css`보다 먼저 로드되므로, **같은 레이어 안에서는 소스 순서가 다시 유효해진다** — `dashboard.css`의 리셋이 나중에 로드되어 여전히 이긴다(전역 margin/padding=0 효과가 유지된다). `.card-body`는 `@layer components`라 `base`보다 우선순위가 높으므로 정상적으로 padding을 받는다. `dashboard.css`의 나머지 규칙(`.input`, `.btn`, `.check-row input` 등)은 여전히 레이어 없이 남아 있어 최우선순위를 유지하고, "서비스가 kit을 오버라이드한다"는 원래 의도한 동작도 그대로 유지된다.

**일반화**: 이것은 agent-gate 국소 문제가 아니다. kit을 쓰는 서비스 9개 전부가 레이어 없는 평범한 CSS를 갖고 있다. 그 안에 전역 리셋이나 범용 규칙이 하나라도 있으면, 그 규칙이 건드리는 모든 속성에서 kit의 컴포넌트·유틸리티 선언은 명시도와 무관하게 항상 진다. 즉 클래스를 정확히 붙여도 서비스 CSS가 조용히 이겨서 아무 일도 안 일어난 것처럼 보인다 — safelist 구멍과 겉보기 증상이 똑같다(스타일이 안 먹는다)는 점이 더 위험하다. 원인 진단을 잘못하면 "safelist에 없나 보다"며 없는 클래스를 찾아 헤매게 된다.

### 4.2 두 번째로 보고됐던 회귀는 실재하지 않았다

Task 6 컨트롤러 시각 검증에서 "체크박스가 브라우저 기본 흰 사각형으로 렌더된다(teal accent-color 소실)"는 회귀가 보고됐으나, fix round에서 재현되지 않았다. `.check-row input { accent-color: var(--accent); }`는 전환 전부터 레이어 없이 선언돼 있었고 새 마크업에서도 셀렉터가 그대로 매치했다. `getComputedStyle(input).accentColor`가 정확히 `oklch(0.78 0.13 185)`로 나왔고 브라우저에서 teal 체크 표시를 직접 확인했다.

가장 유력한 설명은 관찰 시점의 **브라우저 캐시**다 — 재빌드 직후 옛 `dashboard.css`가 캐시에 남은 채로 새 HTML만 받아 보면, `.card-body` 등 신규 클래스에 대응하는 규칙이 옛 CSS에 없어 4.1의 여백 소실과 동시에 나타났을 수 있고, 그 상태에서 미체크 네이티브 체크박스가 흐릿하게 보였을 가능성이 있다. 코드 변경은 하지 않고 주석만 추가했다. **이 항목을 리포트에 남기는 이유는 "회귀로 보고됐지만 실재하지 않았다"는 사실 자체가 다음 파일럿에도 유용하기 때문이다** — 강제 새로고침 없이 판단한 시각 검증은 오탐을 낳는다.

### 4.3 컨테이너 재빌드 비용

`agent-gate` 컨테이너는 `static/`을 `Dockerfile`의 `COPY . .`로 굽는다. 라이브 마운트가 아니다. 정적 파일 하나를 고쳐도 `docker compose up --build -d agent-gate`가 필요했고, 실측 재빌드 시간은 **약 10~17초**, 200ms 폴링 기준 연결 실패(다운타임) 구간이 **약 2.3초**였다. Task 5·6은 각각 편집을 모아 한 번에 재빌드하는 방식으로 대응했다.

### 4.4 Cloudflare 쪽에서 필요했던 작업이 계획보다 많았다

`kit.code0987.me`를 살아 있는 URL로 만드는 데 Caddyfile 수정 외에 Cloudflare 쪽 변경 세 가지가 더 필요했다.

1. DNS CNAME(터널로, proxied)
2. 터널 ingress 규칙 `kit.code0987.me → http://caddy:80` 추가(설정 버전 45→46)
3. **캐시 룰**(`http_request_cache_settings` 페이즈, ruleset `740c570a`) — `browser_ttl`/`edge_ttl`을 `respect_origin`으로 설정

세 번째가 특히 눈에 띄지 않는 실패였다. 캐시 룰 없이는 Cloudflare가 존 전역 기본값(Browser Cache TTL 4시간)을 적용해 origin이 보낸 `max-age=300`을 **`max-age=14400`으로 조용히 재작성**했다 — 응답은 200이고 헤더도 `Cache-Control`이라는 이름으로 존재하니 겉보기엔 정상이지만, 스펙 §8.2가 약속한 "5분이면 전파된다"가 실제로는 4시간이 되어 있었다. `curl`로 `Cache-Control` 헤더의 존재 여부만 확인하고 넘어갔다면 놓쳤을 문제다.

## 5. itad 마이그레이션으로 넘길 것

- **Jinja 매크로 패키지** — 스펙 §9-1은 1단계에 포함했으나, `agent-gate`가 Jinja가 아니라 FastAPI `FileResponse`로 정적 HTML을 서빙해 이 계획엔 소비자가 없었다. `itad`는 Jinja 서비스이므로 여기서 처음 실전 검증된다.
- **checkbox/toggle 컴포넌트** — 이번 파일럿에서 만들지 않기로 한 것 중 가장 확실하게 반복될 구멍이다. 설정 화면이 있는 서비스라면 어디서든 다시 마주친다.
- **표준 마이그레이션 절차의 첫 단계로 "서비스 CSS 리셋을 `@layer base`로 감싸기"를 명문화** — §4.1의 발견이 스펙 §11.1과 마이그레이션 절차 양쪽에 반영됐다(이 문서 §5 갱신 및 kit-design.md §9 참고). itad 착수 전에 `itad`의 기존 CSS에 레이어 없는 전역 규칙이 있는지부터 확인해야 한다.
- **서비스 고유 변수명이 kit 토큰 이름과 겹치는지 확인** — `--radius`뿐 아니라 `--radius-sm`도 agent-gate `:root`가 재정의해 kit의 의도한 값을 가렸다. 토큰 스왑 단계(Task 5에 해당하는 작업)에서 서비스 `:root`의 변수명 전체를 kit `@theme`가 내보내는 이름과 대조하는 점검이 필요하다.
- **`kit lint <service>` 구체화** — 파일럿 두 발견(레이어 충돌, safelist 구멍) 모두 브라우저 렌더링 없이 정적으로 잡을 수 있다는 것이 확인됐다. (1) 서비스 CSS에서 레이어 없는 최상위 규칙을 모으고, 그 규칙이 건드리는 속성과 같은 속성을 설정하는 kit 셀렉터가 실제 HTML에 적용돼 있으면 "그 요소는 클래스가 있어도 서비스 CSS가 항상 이긴다"고 결정론적으로 보고한다. (2) HTML에서 쓰인 클래스와 kit 정의를 대조해 kit 클래스인데 값이 없는 경우만 짚어낸다. 아직 만들지 않았다 — itad 이후, 조용한 실패가 실제로 반복되는지 다시 확인하고 착수 여부를 정한다.
- **`--info`/`--planned` 같은 서비스 고유 의미색의 kit 승격 여부** — 반복 사례가 하나 더 쌓이면 판단한다. 지금은 보류.
